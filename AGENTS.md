# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Prototype Decisions

- This product now includes both the creator-facing COMETS payment portal and a system-administrator workspace focused on user and identity operations.
- Administrators and creators use the same login form without a role selector. The authenticated account's server-owned `ADMIN` or `CREATOR` role determines the destination workspace, and public registration can only create `CREATOR` accounts.
- Treat the administrator workspace as a user and identity operations console, not a payment management console. Administrators manage accounts, invitations, access status, verification, corrections, notifications, audit history, and user-management settings; they do not create contracts or Invoices, approve requests, or execute payments.
- Administrator routes use `/admin`, `/admin/users`, `/admin/users/:id`, `/admin/audit-logs`, and `/admin/settings`. The default administrator landing page is a compact user-operations overview.
- `ADMIN` can inspect creator business data in a clearly labeled selected-user context and may edit basic and social profile data. Administrators cannot sign an Invoice or edit a creator payout account; payout and other sensitive corrections must be returned at field level to the creator.
- Sensitive payout values are masked by default. Revealing a full value requires a reason and creates an audit event. User-list exports remain masked.
- Contracts, Invoices, request projects, and payment status are owned by an external system and enter through a typed, idempotent adapter keyed by immutable Creator ID. Administrator surfaces are read-only for these records.
- Keep creator account access status limited to `ACTIVE` and `DISABLED`; invitation, onboarding, verification, and correction state are tracked separately. Disabling retains data and revokes active access.
- Creator registration activates the account but restricts Invoice signing until social verification is complete. Initial verification is confirmed by an administrator; returned corrections auto-resolve after the creator submits values that pass the applicable validation.
- Apply administrator changes to the local test environment first. Never update `192.168.88.188:8772` unless the user explicitly asks to push.
- The authenticated home route is `/`; `/requests` redirects to `/`. Creators can view but cannot create or approve payment requests.
- Request projects are the normalized project-name intersection of the current account's contracts and Invoices. Request filters, summary totals, status badges, and progress are driven by Invoice status; creator-facing request UI must not use PM-review or finance-review states.
- The request-project home page follows the supplied action-first reference: creator greeting, a two-item `待我处理` band, three compact amount summaries, and a dense request table with inline `合同 → Invoice → 审批 → 付款` progress. This selected screenshot is the source of truth for hierarchy, density, spacing, colors, and desktop composition.
- The `待我处理` band, amount-summary card, and request-project card all use the same white card surface, neutral border, and restrained shadow. The two upper cards do not use colored backgrounds or colored left accents. The `去签署` action routes to `/invoices?status=DRAFT_SIGNATURE`, and the Invoice list initializes with the pending-signature tab active.
- The UI mirrors the management console's light operational design and remains responsive down to 320px.
- Backend integrations are represented by typed service interfaces and a mock adapter.
- Creator registration follows the supplied two-column reference: email, password, optional invitation code, required legal agreement, and Google registration. Personal name is collected during onboarding.
- Creator registration passwords must be 8–20 characters and include uppercase letters, lowercase letters, and numbers without spaces. Special characters are allowed but not required. The registration field states the complete rule and submission is blocked until every requirement passes.
- Creator registration must always leave its loading state after an unsuccessful email or Google attempt. Service errors such as a duplicate email or disabled public registration are shown in the existing form alert so the user can correct the input and retry without refreshing the page.
- Registration actions use the requested light-purple treatment. Social verification supports multiple profile URLs and up to six account-console screenshots, with both collections persisted in the profile model.
- On desktop registration, the creator image stays on the left and the form stays on the right. Registration actions use the COMETS mark's pink and light-purple palette.
- Social onboarding does not ask for a platform or account handle. It requires profile links, backend screenshots, and a successful ownership-verification state before continuing.
- Registration basic information uses the heading `基本信息` without a suffix and the fields `真实姓名 / Real Name`, `联系电话 / Tel`, `联系邮箱 / Email`, and `联系地址 / Address`; the profile mirrors the same field labels.
- The payout section is named “收款账户”. Airwallex is enabled; PayPal and PayerMax remain visible but disabled as “暂未开放”.
- The creator profile supports multiple payout accounts. Each account is a persistent card with its own provider, currency, masked identifier, verification state, and a top-right `MoreHorizontal` menu. The default account keeps a star beside that menu; `设为默认` exists only inside non-default account menus, with no separate section-level default action.
- The creator-facing payout-account section never displays Beneficiary status or Beneficiary generation counts. It uses three persistent channel selectors in the order `Airwallex → PayPal → PayerMax`; selecting a channel shows every account under that channel, while PayPal and PayerMax remain visibly marked as not yet available.
- `编辑档案` and payout-card `编辑账户` are separate edit modes. Account editing keeps social accounts and Invoice contact fields read-only, closes and hides payout-card operation menus, removes the top-right profile save controls, and provides `取消 / 保存修改` only at the bottom-right of the payout-information form.

Every payout account instead has an internal `账户别名` that is separate from the beneficiary/account-holder name. New Airwallex accounts start unnamed and cannot be saved until a 2–40 character alias is provided; existing aliases are editable only through the payout-card `编辑账户` flow, normalize repeated whitespace on save, and update the account-card title after successful persistence.
- During payout-account creation or editing, the alias appears in a standalone `账户配置` card before the payout-scenario card. Its `Internal nickname` field is explicitly identified as an internal MUSE Pay field that is never submitted to the Airwallex Beneficiary API.
- Payout-account deletion is allowed only for draft, incomplete, validation-failed, or pending-confirmation accounts that have no Beneficiary, business linkage, transaction history, or active payment. Verified, Beneficiary-backed, or historically linked accounts are retained and can only be disabled; review, validation, and payment-processing states lock both destructive actions with an explanatory reason.
- A default payout account must be atomically replaced before deletion or disabling. Disabled accounts remain visible, are excluded from new-payment and default-account choices, and can be re-enabled without becoming default. Account mutations must refresh the default account, usable-account count, profile completeness, Beneficiary state, missing-information notice, and no-usable-account empty state.
- Airwallex fields are generated from country, currency, beneficiary type, and transfer method. Schema validation must pass before creating a Beneficiary and persisting its `beneficiary_id`.
- Every Airwallex payout scenario always starts with five required fields in this order: `Account name`, `Account number`, `Bank name`, `Bank address`, and `SWIFT code`. The Form Schema may append other scenario-specific fields, but it cannot remove or make these five optional; synonymous bank-address fields are normalized to one field.
- The saved profile must render the routing fields for the selected transfer scenario instead of showing an irrelevant empty SWIFT field.
- The creator profile does not expose the Airwallex Beneficiary ID. Its three verification-status badges are hidden while editing and restored after a successful save. Saving profile edits uses a blocking validation state followed by an explicit success dialog.
- The profile's certification screenshot action is labeled “上传认证截图” and uses a light-green treatment with the upload icon on the left.
- The sidebar account summary prefixes the creator handle with its current social platform, formatted as `平台 · @ID`.
- Each social-account card derives and displays that platform's own account name from its corresponding profile URL instead of reusing one shared handle.
- Editable profile field labels use the same Chinese / English wording as registration and onboarding. Section titles, descriptions, status badges, and action buttons remain Chinese-only.
- The required profile contact email uses the same email-format rule as registration, shows an inline error while editing, and blocks profile saving when the address format is invalid.
- The Airwallex payout-condition country field is labeled `国家 / Country` in registration and the saved profile.
- Airwallex account names accept only ASCII English letters and single spaces between name parts. Registration input sanitizes invalid characters live, while Schema validation and profile saving enforce the same rule.
- Basic and payout fields collected during registration remain required in the creator profile. - The creator profile follows the management-profile information hierarchy: creator summary, compact overview, social accounts, Invoice contact details, payout channel, a standalone payout-scenario section, and generated payout details.
- Profile-card header icon containers keep the existing 32 px anatomy but use distinct light system tones by section: blush for social accounts, blue for Invoice contact details, green for payout channel, lilac for payout scenario, and amber for Airwallex bank details.
- Country, recipient type, account currency, and transfer method are editable profile fields. Changing any one reloads the Airwallex Form Schema, removes fields that are no longer part of the selected scenario, and makes only the returned required fields mandatory before saving and recreating the Beneficiary.
- Generated Airwallex payout fields use the validation rules returned for the active country, currency, recipient type, and transfer method. Account name, bank account number, bank name, and IBAN show field-level errors on blur and save; IBAN validation covers country code, scenario length, and MOD-97 checksum before the Beneficiary validation call.
- Every generated Airwallex text input places its Schema-derived format requirement inside the input placeholder, covering allowed characters, exact or minimum/maximum length, and separator restrictions. Format hints are not repeated below inputs and do not include examples; registration and profile editing reuse the same rules.
- Generated Airwallex placeholders use a fixed 8.5px size without affecting entered values. Long IBAN requirements use a compact `国家开头｜总位数｜字符限制｜分隔符限制` format so the complete hint fits within the input.
